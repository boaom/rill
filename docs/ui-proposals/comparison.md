> 对象：designer 在 t14 提交的三方向初稿 —— A 日报 Rill Daily / B 此刻 Rill Now / C 格子 Rill Grid
> 作者：verifier（t15）｜**这是基于 t14「未修复」版本的横评**；t22 的缺陷修复与重截尚未并入，缺陷清单以 `polish-log.md` 与 t22 为准。

## 0. 结论（一句）

**A › C › B**。A 是唯一在四种真实内容情形里没有硬崩、且 1440 有真桌面版式的一支；C 密度最好但转发语义在窄栏塌掉；B 审美最锋利，而「一屏一条 + 单张大图」的骨架承受不了真实内容。

## 1. 方法与口径（先说清楚我怎么测的，再说结论）

| 项 | 我的做法 |
| --- | --- |
| 截图 | **不用 designer 的图**。自己起 `node:http` 静态服务（4260/4261/4262），CDP `Emulation.setDeviceMetricsOverride` 打真 375（812 高），1440 用 `--window-size=1440,1043`（headless=new 的窗口含 ~143px 头，减掉才得到 900 视口）。每张图断言 **PNG IHDR 宽 = `innerWidth` = 目标宽** |
| 页面入口 | 三方向原型都支持 `?only=timeline\|detail\|compose` 单屏模式（`.frame.is-on`），我只读渲染、**没有改任何 designer 文件** |
| 可读性 | `getComputedStyle` 逐文本节点取 `fontSize` / `color`，背景色沿祖先链做 alpha 合成（半透明层逐层 over），再算 WCAG 对比度；**并用截图像素复核**（在正文矩形内取众数背景色重算），两法互相验证 |
| 正文口径 | 用 `src/data/mock.json` 的真实正文去命中 `[data-part="body"]`，命中的才算「正文」；元信息（时间戳/句柄/计数）按「标签」口径判 |
| 红线 | 源码 grep（`http(s)://`、`<img`、`@font-face`、`base64,`、`Unique\|微博\|Weibo\|sina`）+ 运行时 `document.body.innerText` 扫禁用串 + CDP `Network` 统计请求是否越站 |
| 内容压力 | 运行时注入（**不改文件**）：把首条正文换成 240 字、把图格克隆到 9 张、隐藏全部卡片看空态；记录裁切/溢出/是否有展开口 |

补充一条被本项目踩过两次的坑：**「设计稿上看不出会不会塌」**。所以下面「真实内容鲁棒性」一列，凡是我实跑过的都标 `截图/度量实测`，只有读代码得来的标 `结构实测（纸面）`。

## 3. 真实内容鲁棒性（**这一列比好看更重要**）

判定：✅ 能扛 / ⚠️ 能显示但有损 / ❌ 会塌。括号里是依据来源。

| 内容情形 | **A** | **B** | **C** |
| --- | --- | --- | --- |
| **转发卡**（正文 + 原博嵌卡） | ✅ 详情内 quote 335×100，`clamp=none`，原博正文 **不裁切**（截图/度量实测） | ⚠️ 详情内 quote 335×107.5 成立，但全页**没有 `[data-card]` 列表** → 转发帖与原博被拆成两个整屏，关联只能靠记忆（结构实测 + 读图子代理判词一致） | ❌ 双列窄卡（166.5 宽）里原博被压到 126.5×105.2，正文 **3 行截断**（`pClip=true`，29 字被裁）；且**详情页没有内嵌原博**（`.cc__quote` 只在时间线）（度量实测） |
| **九宫格**（1–9 图） | ✅ 原生 3×3：335×335、格 111×111、9 张全可见；注入 9 图后媒体块 335 高，仍在屏内（−124px）（度量实测） | ❌ 注入 9 图后媒体块 **1875px**，超屏底 **1191px**（度量实测） | ⚠️ 整宽卡 3×3 成立（343×343、格 111.7）；半宽卡只有 1 个封面 + 「9 图」角标 → 图多即信息降级（度量实测） |

## 4. 可读性实测明细（skill 红线：正文 ≥14px、标签 ≥12px、对比度 ≥4.5:1）

| 方向 | 正文（mock 命中 `[data-part=body]`） | 最小字号 | 最小对比度（全元素） | 正文对比度（计算 / 像素复核） | 不达标元素 |
| --- | --- | --- | --- | --- | --- |
| A | 16px | 12px（仅标签） | **5.64** | 19.68 / **19.52** | **0** |
| B | 16px | 12px（仅标签） | **4.88** | 17.68 / **17.68** | **0** |
| C | 16px | 12px（仅标签） | **4.57**（详情「回复 · 3 条」） | 18.04 / **17.89** | **0** |

三方向都**没有**低于红线的元素：正文一律 16px，字号最小的 12px 只出现在时间戳/句柄/计数器这类元信息上（符合「标签 ≥12」）。C 的 4.57 离红线只有 0.07，是唯一值得盯的余量。

我最初把「≥8 字」当正文判据，会误报 12px 的时间戳（如 `2026 周一 · 30 条 / 12 人`），所以改用「mock 正文命中」定位正文——口径更硬，结论也更干净。

## 6. tokens 与迁移成本：我独立核对的结果（含偏差）

| 方向 | `tokens.md` 声明 | 我的实测 | 判断 |
| --- | --- | --- | --- |
| A | 变动 42 个 token；组件 CSS 186 行（原型 CSS 203） | 变动 **39** + 新增 **7** + 弃用 22；组件 CSS **214** 行（style 237 − `:root` 23） | 量级一致（都是「换 tokens + 局部重写」），**明细不吻合**：变动+新增 46 ≠ 42；行数因注释/空行/暗色派生块口径不同 |
| B | 变动 40；组件 139 行（156） | 变动 **40** + 新增 2 + 弃用 22；组件 **183** 行（203） | 变动数完全吻合；**行数偏差最大（183 vs 139）**，建议 `tokens.md` 补口径 |
| C | 变动 31；组件 166 行（183） | 变动 **29** + 新增 1 + 弃用 22；组件 **201** 行（219） | 量级一致，差 2 个 token（可能是暗色派生未计入） |

**结论**：三个「迁移成本」都属同一量级（几十个 token + 一两百行组件 CSS），不改变选型；但**行数不能当作精确预算**，需要 builder 以真实文件 diff 复核。B 的偏差最大，若选 B 要重新估。

## 7. 推荐排序

1. **A · 日报（推荐）**：唯一在「转发 / 九宫格」两种真实内容上实测不塌的一支，1440 有真正的三栏报纸版式（日期栏 300 / 正文 736 / 侧栏 260），可读性三支里最好（正文 19.68:1）。代价是密度低、圆角归零与现有 tokens 冲突最大、要新增 7 个 token。
2. **C · 格子**：最稳、最省（只换色板）、密度最高（一屏 6 卡）。但转发语义在窄栏里会塌（原博 3 行截断）、详情页丢原博、1440 没有桌面设计——对「转发/引用」是核心行为的 feed 来说，这是结构性问题。
3. **B · 此刻**：审美上限最高（深色 67%、86px 时刻字、零彩色），但它把「一屏一条」当成了骨架；九宫格、长文、转发链都会把它撑破，1440 只是拉长的手机。适合做「单条详情/沉浸阅读」的实验，不适合当主界面。

**如果用户更看重 X**：
- 更看重**信息密度 / 像中文内容产品** → 选 **C**（代价：转发语义、1440）。
- 更看重**一屏一条的沉浸感** → 选 **B**（前提：先解决九宫格与长文承载）。
- 更看重**真实内容不出洋相 / 桌面端像样** → **A**（本轮验收结论）。

## 8. 已知缺陷与后续

- 本轮结论基于 **t14 未修复版本**。t13 打磨环已修的三处（C5 搜索提示对比度 4.33→5.34、C4 宽图被 tabbar 切、C2/C6 相似度高）在本轮实测里**已生效**（C 的搜索提示 6.69:1）。
- 读图子代理另列 15 条缺陷（含 5 条 high：B 纯黑发博预览、B 转发双整屏无关联、B 九宫格占满整屏、B 的 1440、C 九宫格被拆坏），与我的度量结论方向一致；**具体修法与终态以 t22 为准**。
- 修复后必须复验的项（我会按同一套口径重跑）：九宫格 9 图、长文折叠/展开、转发卡原博不裁、空态文案、1440 桌面版式。

> **时间戳注意（诚实声明）**：我的 14 张截图取自 **15:21–15:31** 的 t14 版本；designer 的 t22 修复已在 15:29 之后陆续改到 `A/index.html`（15:37）、`B/index.html`（15:35）、`C/index.html`（15:29），当前文件哈希已与我的截图不同。所以本档案的图**只对应截图那一刻**，与现在磁盘上的文件不再一致——这不是失误，而是「基于未修复版本」的定义。终版横评等 t22 完成后按 captain 排期重跑。

## 9. 一条与横评相邻但会影响观感的事实（顺手记下）

在线模式下 **「关注」tab 只有 8 条、「推荐」tab 20 条**（`/api/timeline?tab=friends` → `items=8 hasMore=false`；`tab=recommend` → `items=20 hasMore=true`），而**离线 UI 固定 20 条**（`data-post-count=20`）。这不是 bug（following 是 8 人子集，分页 20/页），但用户从在线切回离线会觉得「数据变多了/变少了」。建议：**tab 上直接标条数**（`关注 · 8` / `推荐 · 20`），或首次切换时给一句说明。
